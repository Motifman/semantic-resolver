# 初版の設計判断

## 1. 候補をツールスキーマから分離する

共通プロンプトを再利用したい主モデルへは、固定したツール定義と、その後ろにある
現在状態・候補を渡す。出力を解決するための短い要求だけが、動的な候補を扱う。
ライブラリはモデル API の要求を書き換えず、候補と文脈を受け取るだけにする。

動的 enum による制約生成も有効な代替である。主モデルのキャッシュと両立でき、
追加の意味判断より安く正確に解決できる環境では、そちらを使う。

## 2. 呼ぶタイミングは利用者が決める

公開名は `SemanticResolver`。呼ばれたら意味判断を行い、完全一致や別名による
省略を内包しない。呼び出し条件と意味判断を一つにすると、既存の解決処理へ
差し込みにくくなるため。候補なしだけは判断の対象がなく、通信しない。

完全一致でも呼びたい用途と、未解決値だけ救いたい用途の両方を扱える。
後者は利用者側で既存の完全一致・表示崩れ補正を先に行う。

## 3. 対応なしを常に扱う

候補が存在することと、入力に対応する候補が存在することは異なる。
候補が一件でも、意味が異なれば棄却する。「配線を締める」を「発電機を点検する」
へ変換して、別の行為の成功で誤りを隠してはならない。

内部で対応なしの選択肢を追加し、公開契約では `None` に戻す。利用者が毎回追加する
方式は入れ忘れが起きるため採らない。予約文字列は作らず、実際の候補と衝突する場合は
通信内の名前を変える。文脈は曖昧さを絞る情報であり、入力を無視した再計画には使わない。

## 4. 評価値と採用基準を分ける

`Judgment[Evidence]` は方式固有の評価値を保持する。`Policy` が採否を決める。
Jev の分布の集中度と、埋め込みの類似度を共通の「確信度」に押し込めない。
初版は `JevEvidence` / `JevPolicy` と、差し替え用の小さな Protocol だけを持つ。

Jev の閾値は利用者が明示する。同率を先に棄却し、最大確率と確信度の両方を確認する。
これらは独立した二つの正しさの証拠ではなく、実データで調整する採用条件である。

## 5. 棄却・障害・入力不備を分ける

`Unresolved` は正常な意味判断の棄却、または候補なし。通信や応答形式の問題は
`BackendError`、入力不備は `ValueError` / `TypeError`。
障害を対応なしへ落とすと、機能停止と適切な棄却が区別できなくなるため。

提案値、評価値、閾値、所要時間、モデルを結果として返す。ライブラリは保存先を持たず、
利用者が自分の観測記録へ載せる。API の応答本文を例外文へ写さない。

## 6. 初版は同期接続と一回の要求に絞る

Jev 接続は追加依存の `httpx` だけを使う。公式の Choice HTTP 契約が小さく、
真偽判断や点数評価を含む SDK 全体は必要ないため。API 変更へ追従する費用が
大きくなれば公式 SDK を使う判断を見直す。

自動再試行は持たない。待ち時間の上限と再試行回数を利用者の処理から見える形にする。
非同期・複数要求の一括処理は、実際の利用側で必要になったときに追加する。

## 7. llm-rpg の固有処理は外に残す

対象の名前解決、表示行の補正、操作の収集、実行条件検証、ゲームの trace、
エージェントへの結果通知は llm-rpg が担当する。
このリポジトリの初版では llm-rpg 自体を変更しない。

導入時は `ActionNameRescue` の接続を置き換える別 PR とし、既存の設定・記録との
対応を確認する。特に現在の候補集合は「存在するが今は実行できない操作」を含む。
ライブラリへ移す際に勝手に削らず、意味解決と実行条件を分けたまま保つ。
